## 1. 目的と境界

まずStratocaster系のギターパーツ取付工程を対象に、製品仕様から必要な作業を判断し、現場で作業と検査を記録できるようにする。

将来的には製品詳細ページを現場で参照できる「電子仕様書」とする。Phase 6Aで全製品系列・全工程の専用画面まで展開することは意味しない。調整・調音、最終検品、Body・Neck専用工程への展開は後続計画とする。

この文書では、ユーザーが示した基本方針と、詳細設計で決める事項を区別する。クラス名や列名の候補を確定済みスキーマとして扱わない。

## 2. 開発単位

| 段階 | 目的 | 設計・確認する内容 |
| --- | --- | --- |
| 6A-1 製品仕様拡張 | ギターパーツ取付の作業内容を判断できる仕様を製品マスタに持たせる | 既存項目の再利用、不足仕様、入力・詳細表示、DB保存方法 |
| 6A-2 工程内作業記録基盤 | 汎用履歴と工程固有記録を分離する | 履歴との関連、開始時の作業項目確定・保存、実績・検査・途中保存の記録構造 |
| 6A-3 専用画面・工程連携 | 工程ページ内で作業から終了まで行う | 分岐表示、チェック、OK / NG、NGコメント、再表示、完了判定、既存工程終了処理への接続 |

### 2.1 6A-1の保存構造

`Product` 1 : 0..1 `ProductPartsSpec`の任意1対1構造を第一案として採用する。Bridge / Tuner / Electronics / Stringのパーツ取付関連仕様をまとめ、Product本体へPhase 6A固有項目を大量追加しない。Phase 6Aでは領域ごとの追加テーブル分割は行わない。

これは設計方針の採用であり、Entity・物理テーブル・FK・JPA関連の実装は未着手。具体的な列長、選択肢、必須制約、保存・取得方法は実装設計で確定する。

### 2.2 ProductPartsSpecの正式候補

「必須候補」「任意候補」は現段階の方向であり、DBのNOT NULL制約を確定するものではない。

| 領域 | 項目 | 型・用途・入力方針 |
| --- | --- | --- |
| Bridge | `bridgeType` | Enum / 固定コード候補。6点支持 / 2点支持 / Floyd Rose等の作業分岐 |
| Bridge | `bridgeModel` | String。使用部品を特定する情報。任意候補 |
| Bridge | `requiresStudHoleExpansion` | Boolean。true＝必要、false＝不要、null＝未設定。2点支持時の穴拡張が常に必要か製品依存か未確定のため、現時点では仕様値として保持する方向 |
| Tuner | `tunerModel` | String。使用ペグの特定。必須候補 |
| Tuner | `tunerMountingType` | Enum / 固定コード候補。作業分岐に使用 |
| Tuner | `tunerBushRequired` | Boolean。true＝必要、false＝不要、null＝未設定 |
| Tuner | `tunerLayout` | Enum / 固定コード候補。初期対象は6連を想定し、将来差異に備える候補 |
| Electronics | `selectorPositions` | Integer。全ポジション確認に使用 |
| Electronics | `controlLayout` | String。例：1Vol / 2Tone。現時点では表示・確認用。個別コントロール検査の構造化が必要になれば再設計 |
| Electronics | `jackType` | Enum / 固定コード候補。具体的な選択肢は詳細設計で確定 |
| String | `stringMaker` | String。任意候補 |
| String | `stringModel` | String。指定弦の特定。必須候補 |
| String | `stringGauge` | String。`.009-.042`等のセット表記を扱う。必須候補 |

既存`Product.pickupLayout`を再利用し、同義項目をProductPartsSpecへ追加しない。

`bridgeInstallationProcess`は追加しない。「Floyd Roseならブリッジ本体は調整・調音工程で取り付ける」等は、Bridge仕様から決まる作業ルールとしてService側で扱う方針とする。具体的な分岐・作業順は後続設計で確認する。

`tunerType`は追加しない。Kluson / Schaller等がメーカー、構造分類、取付方式のどれを表すか曖昧なため、まず`tunerModel`・`tunerMountingType`・`tunerBushRequired`で作業判断する方向とする。

### 2.3 対象製品の識別

製品名・モデル名等の文字列推測は使用しない。既存InstrumentTypeMasterとMES内部モデルコードの正式な分類体系、および`resolveProductClassification()`相当の処理を再利用して`ST`を判定する方向とする。コードが解決できない場合も名称から補わない。

6A-1のためだけにProductへInstrumentTypeMasterの新規FKを追加しない。直接FKによる正規化は、将来必要になった場合に別途検討する。

### 2.4 バリエーション登録

現行の「共通仕様＋複数バリエーション」という入力構造を維持し、パーツ仕様は登録UI上では基本的に共通入力とする。ただし保存時には各Productが独立したProductPartsSpecを持つ。

共通入力からProduct A＋Spec A、Product B＋Spec B、Product C＋Spec Cを作成し、同一Specを複数Productで共有しない。将来のProduct単位の個別仕様に対応できる構造を維持する。

### 2.5 既存Productの初回補完と編集制限

`ProductPartsSpec == null`は「パーツ取付仕様未設定」を意味する。既存Productにはこの状態を許容し、仕様を推測して一律補完しない。

Phase 6A導入以前から存在するProductには、初回仕様補完を許可する方向とする。

| 状態 | 取扱いの方向 |
| --- | --- |
| 導入前から存在するProductでSpec未登録 | 初回仕様補完可 |
| Spec登録済み・製造開始前 | 編集可 |
| Spec登録済み・製造開始後 | 編集不可 |

これは既存Productを電子仕様書化するための初回補完であり、製造開始後の仕様変更を恒常的に許可する例外ではない。Product本体の既存製造仕様の変更制限も維持する。

現行ServiceのGuitar発行・生産計画の開始／完成数量に基づく制限との接続、導入前Productの識別方法、導入後のSpec未登録Productの扱いは実装設計で再確認する。Specの削除・再登録によって初回補完扱いへ戻せないこと、同時初回登録の扱いも設計する。

### 2.6 仕様未設定の扱い

Product自体の登録・存在は許可する。電子仕様書ではSpec未登録時に「パーツ取付仕様：未設定」と識別できる構成を目指す。

6A-2 / 6A-3では、ギターパーツ取付作業開始前に必要仕様が揃っているかServiceで検証し、不足時は作業開始を止める方向とする。未設定仕様から作業内容を推測しない。具体的な必須条件と検証の接続点は後続設計で確定する。

## 3. 情報の責務分離

| 情報 | 意味 | Phase 6Aの扱い |
| --- | --- | --- |
| 製品仕様 | 何を作る製品か | ProductPartsSpecにパーツ仕様を保存し、既存Product.pickupLayoutも再利用する |
| 作業指示 | その仕様なら何をする必要があるか | 製品仕様からService側のルールで必要作業を決定する方向で検討 |
| 作業実績 | 実際に何を行ったか | チェックや途中保存を工程内作業記録として保持 |
| 検査結果 | 結果がOK / NGのどちらだったか | 作業実施のチェックと区別し、NGコメントも記録 |

作業項目定義そのものをPhase 6AでいきなりDBマスタ化しない。これは「実行時に確定した作業項目をDBに保存しない」という意味ではない。実行時の指示と記録は保存し、再表示で復元できる構造にする。

既存`ProcessHistory`はGuitar・工程・作業者・開始日時・終了日時を管理する汎用履歴として維持する。工程固有のチェック項目や検査結果を直接追加しない。

別層の名前は`ProcessWork` / `ProcessWorkItem`等を候補とする。履歴に対応する作業記録と、その配下の確定済み項目・実施結果を表現する方向で検討するが、関連の多重度、具体的なEntity名、DB列は未確定。旧ロードマップの`ProcessTaskDefinition` / `ProcessTaskHistory`は旧候補であり、そのまま実装する指示ではない。

## 4. 最初の対象作業

| 作業グループ | 製品仕様による分岐・対象作業 |
| --- | --- |
| トレモロユニット・スプリングハンガー取付 | 6点支持 / 2点支持 / Floyd Roseで作業内容を分岐 |
| ピックガード・舟形ジャック取付 | 穴加工、配線、半田付け、PU音出し、セレクター全ポジション確認、コントロール確認、不具合確認、固定 |
| ペグ取付 | 使用ペグ（tunerModel）、ブッシュ有無、固定方式によって分岐。Kluson / Schaller等を曖昧なtunerType分類として追加しない |
| 弦巻 | 製品仕様に登録された指定弦を使用 |

これらは作業グループと分岐軸の指定であり、個々の必須チェック、検査基準、作業順、数値規格をすべて確定したものではない。穴寸法、締付値、弦ゲージなどを推測で設定しない。

## 5. 開始時点の作業項目の保存

目指す流れ:

1. 作業開始時点の製品仕様を参照し、必要仕様の不足をServiceで検証する。不足時は開始しない。
2. Service側のルールから、その個体に必要な作業項目を決定する。
3. 決定した項目を工程内作業記録側へ保存する。
4. 途中保存・再表示・完了判定では、保存済みの項目を使用する。

後から製品マスタを変更しても、開始済み個体の作業内容が勝手に変わらないことを原則とする。画面を開くたびに最新マスタから項目を再生成する方式は、この原則と整合しない。

確定項目に加えて、分岐根拠の仕様値、表示文言、ルールの版などをどこまで保存するかは6A-2で判断する。「作業開始」が既存工程開始と同時なのか、専用画面での作業開始なのかも設計時に確定する。

## 6. 専用画面と既存工程処理の接続

6A-3の対象機能は、必要作業の表示、作業チェック、OK / NG検査、NGコメント、途中保存、完了条件判定、工程終了。

工程終了そのものは既存`ProcessService.endProcess()`を再利用する。工程遷移、履歴終了、業務日時や完成数量更新を専用画面側へ複製しない。完了条件は画面だけでなくService側で判定する。

必須作業が未完了なら工程終了できないというロードマップの原則を維持する。ただし、NG時の終了可否、再検査、コメント必須条件、必須・任意項目の区別などは詳細仕様が必要。既存の個別・一括終了や直接リクエストが完了条件を迂回しない接続方法も、6A-3着手前に決める。

作業記録の保存と工程終了のトランザクション境界、途中保存と終了の同時操作、二重終了・作業項目の重複生成の防止は、既存の排他・全件検証方針と照合して設計する。

## 7. 段階ごとの完了判定の観点

- **6A-1**: 対象製品について分岐・指定弦の判断に必要な仕様を保存・参照できること。既存製品の未設定値の扱いを決めること。
- **6A-2**: 汎用履歴と工程固有記録が分離され、必要項目が開始時点で保存されること。途中保存・再表示で復元でき、製品変更で開始済み記録が変化しないこと。
- **6A-3**: 各分岐の必要作業と検査を記録でき、確定した完了条件をServiceで判定して既存工程終了に接続できること。

実装時の検証候補は、仕様分岐、仕様未設定、開始後のマスタ変更、途中保存と再読込、未完了・NGの終了制御、個別・一括経路、同時保存・終了、既存工程の回帰。具体的なテストは各段階の仕様確定後に作成する。検証の責任分担・E2E専用DB・fixture cleanupはAGENTS.mdに従う。

## 8. 実装前に決める事項

1. 第2節の正式候補の具体的なEnum / 固定コード、文字列長、数値範囲、必須条件、部分入力の可否、物理スキーマ・関連保存方法。
2. 既存分類処理によるST判定の接続と分類不能・未対応仕様の扱い。新規FKや名称推測は採用しない。
3. 初回補完の対象識別・同時登録・編集制限のService実装、導入後の未登録Productの扱い、既存の製品重複判定とパーツ差異の整合性。
4. 各分岐の具体的な作業項目、必須・任意、検査基準、NGコメント条件。
5. 作業開始のタイミングと、確定項目・仕様の保存範囲、版の扱い。
6. `ProcessHistory`と別層の関連、再作業・再検査時の記録単位。Phase 8の品質管理を先回りして全面実装しない。
7. 途中保存の未入力表現、完了条件、NG時の終了可否、保存・終了の排他とトランザクション。
8. 既存の汎用・一括終了経路と、対象外製品・開始済み履歴との互換性。

今回行うのは設計判断の文書化のみ。Java・HTML・SQL・DB・テストは変更しない。変更内容をChatGPTで確認してから6A-1-1へ進む。確認前に後続実装へ進まず、確認後も具体的な実装範囲はユーザーの指示に従う。
